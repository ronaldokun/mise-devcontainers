01 / Mental model

Two artifacts, one release path

The image contains the operating system and shared development environment. The template is a small project-facing package that tells Dev Container tools how to use that image.

CONTAINER IMAGE

Runtime environment

Built from distros/. It installs system packages, mise, shell setup, users, Docker-in-Docker helpers, and common tools. Images live at ghcr.io/<owner>/mise-devcontainer-<distro>.

DEV CONTAINER TEMPLATE

Project configuration

Built from templates/. It supplies .devcontainer/devcontainer.json and helper scripts. Templates publish to a collection such as ghcr.io/<owner>/mise-devcontainers/<distro>.

Keep project runtimes in the project.

The shared image installs baseline tools. Project-specific language versions belong in the project's mise.toml, not in this image.

PR OPENED / UPDATED

Change detection picks affected distros. CI builds candidate images, assembles templates, and starts each template for tests.

PR MERGED

Release restores validation metadata for the exact merged commit, promotes tested images, then publishes tested templates.

CONSUMER

A developer applies the template. Its config references the released image by immutable digest.

03 / Choose an extension

Small change? Keep it local

Add a shared CLI tool

Add it to distros/_common/.config/mise/config.toml if mise manages it. This changes every image. Put OS-level dependencies in distro package scripts instead.

Add one distro package

Edit that distro's scripts/02-packages.sh. Follow its native package manager: for example, apt-get on Ubuntu/Debian or apk on Alpine.

Change project behavior

Edit templates/_common/.devcontainer/devcontainer.json or its helper scripts. Check mounts, lifecycle commands, and SSH agent forwarding before changing defaults.

Change one published template

Edit templates/<distro>/devcontainer-template.json. Keep its id aligned with the directory name; the publisher validates this.

Shared changes rebuild all distro images.

scripts/detect-changes.sh treats changes under distros/_common/, templates/_common/, or changes to .rebuild-all as a full rebuild. A distro-local change selects only that distro.

04 / Image workflow

How a container image gets assembled

  1. Discover distros. scripts/lib.sh scans direct subdirectories of distros/, excluding _common.
  2. Overlay files. prepare_overlay copies common files first, then distro files over them into .tmp/.build-image-<distro>/. A distro file with the same relative path overrides the common file.
  3. Join Dockerfiles. build-image.sh writes the distro Dockerfile first, then appends distros/_common/Dockerfile. The distro file supplies the base FROM; shared instructions add the environment.
  4. Build and push. Docker Buildx pushes the image under a temporary ci-<run-id>-<attempt> tag. Registry cache is stored under :buildcache.
  5. Promote after merge. promote-image.sh points the release version, :latest, and :current at the exact candidate image.

Shared build order

Common Dockerfile copies and runs the staged scripts in order: 00-config.sh, 01-base.sh, 02-packages.sh, 03-user.sh, 04-mise.sh, and 05-antidote.sh. The first two scripts are distro-provided; common setup supplies later phases. Distro overlays can replace common paths.

Build secrets stay build-time secrets.

MISE_GITHUB_TOKEN enters the image build as a BuildKit secret for mise installs. It is not a Dockerfile ARG or baked image environment value. The template separately forwards an optional host token at runtime.

05 / Template workflow

How an image becomes a template

  1. Overlay template files. create-template.sh copies templates/_common/ and then templates/<distro>/ to .tmp/.publish-template-<distro>/.
  2. Inject release values. It sets the generated Dev Container name, candidate image reference, and template version. This ensures the test uses the image built for that validation.
  3. Start and test. test-template.sh creates a temporary SSH key/agent if needed, copies the generated .devcontainer/, runs up.sh, then runs test/<distro>/test.sh inside the container.
  4. Publish after validation. The release script downloads the tested template artifacts, restores unchanged templates, verifies IDs and release versions, and checks candidate/current image digests match.
  5. Pin and publish. For changed distros, the config is rewritten to ghcr.io/<owner>/mise-devcontainer-<distro>:current@sha256:<digest>. Dev Container CLI publishes the collection to GHCR as OCI artifacts.

Template config details worth preserving

  • workspaceFolder and workspaceMount mount the local project at /code/<project>.
  • SSH_AUTH_SOCK is mounted from the host. Private SSH keys remain on the host.
  • MISE_GITHUB_TOKEN is optional at runtime and forwarded from the host environment.
  • postCreateCommand, postStartCommand, and postAttachCommand invoke scripts shipped in the image.
  • Use devcontainer templates apply for this repo's published template. Its README explains why an editor's template-creation flow may not have the host SSH socket available.
Apply a published template
devcontainer templates apply \
  -t ghcr.io/<owner>/mise-devcontainers/ubuntu \
  -w .

For the upstream collection, the owner is currently mkvlrn. Replace the owner and collection with your own values after forking.

06 / Local build and test

Run the same stages before opening a PR

Local validation uses the same scripts as Actions. It pushes a candidate image, so it requires Docker Buildx and write access to the configured GHCR packages.

Prerequisites

  • Docker with Buildx, jq, and an authenticated GHCR account with package write access.
  • devcontainer CLI for template tests and publishing.
  • oras for restoring previously published template artifacts during a partial release.
  • A loaded SSH key/agent for realistic template tests. The test script can create a temporary test key and agent when absent.
  • An optional MISE_GITHUB_TOKEN for mise operations that need GitHub-backed downloads or higher rate limits.

Build one candidate, generate its template, then test

Commands — replace tag and distro as needed
export GHCR_USERNAME="YOUR_GITHUB_USERNAME"
export GITHUB_TOKEN="YOUR_GHCR_PACKAGE_WRITE_TOKEN"

./scripts/login-ghcr.sh
./scripts/build-image.sh --distro ubuntu --candidateTag local-check

./scripts/create-template.sh \
  --distro ubuntu \
  --candidateTag local-check \
  --imageVersion 2026.10.6-12.00.00

npm install -g @devcontainers/cli
./scripts/test-template.sh --distro ubuntu

build-image.sh pushes its result. create-template.sh writes ignored temporary output. test-template.sh starts the resulting devcontainer and removes its temporary test workspace on exit.

Local tags are not release versions.

The timestamp passed to create-template.sh is only test metadata. The real version is generated by detect-changes.sh during PR validation and saved with the candidate tag and commit SHA.

Change detection sanity check

In CI, base and head SHAs come from the pull request event. Locally, absent those values the script compares HEAD~1...HEAD. You can override both:

Compare a chosen commit range
BASE_SHA=<base-sha> HEAD_SHA=<head-sha> ./scripts/detect-changes.sh
07 / GitHub Actions release

A merge releases the tested bits

Workflow / jobWhat it doesKey output
validate.yml — detect-changesRuns publishing logic tests, selects affected distros, creates candidate tag and image version, stores metadata artifact.Distro matrix + release metadata
build-imageLogs into GHCR and builds/pushes each affected image candidate.:ci-<run>-<attempt>
create-templateCreates one candidate-configured template per affected distro and uploads it as an artifact.template-<distro>
test-templateDownloads each template artifact and runs it against its candidate image.Pass/fail validation
release.yml — restore-validationRuns only for merged PRs. Finds a successful validation for that exact head SHA and downloads its metadata and template artifacts.Verified candidate + tested artifacts
promote-imagePromotes candidate to version, latest, and current.Stable image tags
publish-templateCombines changed templates with existing unchanged templates, verifies digest identity, pins changed configs, publishes collection.Versioned OCI templates
Validation metadata binds release to tested commit.

The artifact records distro list, candidate tag, image version, and PR head SHA. Release looks up successful validation for that SHA. If the PR changes after validation, the new head must pass validation before merge.

First release needs every template published.

Publishing a partial distro update pulls the existing :latest template artifact for every unchanged distro. For a new collection, change .rebuild-all so validation and release include every distro. Otherwise publishing fails until all collection members exist.

Validation metadata and template artifacts have 30-day retention. Merge while the successful validation run and artifacts remain available.

08 / Publish under your account

Fork once, then rebrand the registry paths

The workflow logic is reusable, but this repo currently hard-codes upstream package and template namespaces. A fork alone will still try to publish upstream names.

Update the namespace references

FileUpdate
scripts/lib.shChange image_name() from mkvlrn/mise-devcontainer-<distro> to <your-owner>/mise-devcontainer-<distro>.
scripts/publish-template.shSet NAMESPACE to <your-owner>/<your-template-collection>.
templates/*/devcontainer-template.jsonUpdate publisher, documentationURL, and licenseURL for your project.
distros/_common/DockerfileUpdate org.opencontainers.image.source to your repository URL.
README.mdUpdate image/template examples, badges, repository links, and any owner-specific instructions.

The image and template namespaces are different by design: image packages use a distro-suffixed package name; template packages live under one collection namespace with distro tags. Keep both references consistent.

Set up GitHub and GHCR

  1. Enable GitHub Actions for the fork and allow workflows to create packages. The workflows request packages: write where they push images or templates.
  2. Ensure the workflow's GITHUB_TOKEN can publish packages in your repo/organization. For private packages, make sure template consumers can pull both template artifacts and referenced images.
  3. Add MISE_GITHUB_TOKEN as a repository Actions secret only if builds need it. The workflow passes it as a BuildKit secret, not as a public image value.
  4. For a fork's initial release, update .rebuild-all and merge a validated PR that publishes all distros and seeds all template artifacts.
  5. Check the Actions run and GHCR package pages. Then apply one of your templates to a throwaway project and confirm the image is pullable.
Fork pull requests may not have package-write secrets.

GitHub restricts secrets and write tokens for many pull requests from other repositories. Validate from branches in your own repo or adjust the workflow security model deliberately. Do not grant untrusted PR code a privileged token just to make candidate pushes work.

Also update Renovate configuration if you keep it.

.github/renovate.json extends config from mkvlrn/ts-tools. Replace it with your own config or remove the extension if it does not apply.

09 / Add a distro

Make the image and template a complete pair

Distro discovery is dynamic, but release publication expects a complete template collection. Add every matching component before relying on automated releases.

  1. Create distros/<name>/Dockerfile with a pinned base image and any required distro-specific environment settings.
  2. Add required ordered scripts, usually scripts/01-base.sh and scripts/02-packages.sh. Make scripts executable where the Dockerfile expects them; follow neighboring distro conventions.
  3. Create templates/<name>/devcontainer-template.json. Set id exactly to <name> and fill in name, description, publisher, documentation, and license metadata.
  4. Create test/<name>/test.sh. Source the shared test utilities and base tests, then add distro-specific checks where they matter.
  5. Review the image name and template namespace behavior. lib.sh derives image references from distro names; the collection publish script includes all discovered distros.
  6. Change .rebuild-all for the initial publication. This builds and tests all images and creates all template artifacts, allowing the release job to seed the full collection.

10 / Troubleshooting

Common failure points

SymptomLikely causeCheck
No distro jobs runChanged path is outside watched directories.Review detect-changes.sh; touch .rebuild-all for an intentional full rebuild.
GHCR push deniedWrong hard-coded owner, insufficient token scope, or fork PR token restrictions.Check scripts/lib.sh, package permissions, workflow run context, and package visibility.
Candidate image not found during template testBuild did not push candidate, candidate tag differs, or package is private to the runner.Compare build output and the candidate image value generated in create-template.sh.
Template tests lack SSH accessHost agent/key not available, or template apply path does not expose host SSH_AUTH_SOCK.Check ssh-add -L, template mounts, and use the Dev Container CLI flow in the README.
Release says an unchanged template cannot be restoredCollection has never published that distro, or its OCI package is not readable.Seed the full collection with .rebuild-all; check NAMESPACE and GHCR access.
Release rejects candidate/current digestCandidate wasn't promoted or promotion did not preserve the tested image digest.Inspect promote job and compare both image digests. Do not bypass this guard.
Successful PR validation cannot be restoredValidation was for a different head SHA, or artifacts expired.Re-run validation on the exact merged head and merge within artifact retention.
